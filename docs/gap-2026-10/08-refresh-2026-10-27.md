## 0. 一页结论

1. **入场券已经拿到，而且这两天又补了七块。** 自 06 之后落地：BYOK 全链路（10-26）、记忆模块 P0–P2、对话压缩 `run.compacted.v1`、S1 step 投影、LocalSandboxProvider、tool-service 的 fetch/审计、技能包 + SKILL.md 骨架，以及 10-27 的会话内执行现场（文件树 / 查看器 / 沙箱终端）。单 run 闭环之外，平台骨架（多租户、事件溯源、审批、沙箱、计量、网关）已经齐了。
2. **剩下的差距不在「有没有某个功能」，而在六处「形状不对」**——这是与 2026-10 主流 harness 的真正代差：

### 3.1 值得单列的两个形态参考

- **OpenCode 的 client/server 拆分**与 beauty-moon「desktop 本地模式 + web 云端模式」最同构：agent 跑在常驻 server，terminal/IDE/远程机器都是 client。若要做 CLI/IDE 接入（P2），这是现成的架构参照，不必重造。
- **OpenHands 转型 ACP 聚合器**说明另一条路：harness 与宿主解耦、把 ACP 当接入面。beauty-moon 的事件流 → SSE → 前端已经具备 AG-UI 的同构基础，**AG-UI 是性价比最高的下一协议**（interrupts/state 与现有审批/run 状态几乎一一对应），A2A 排在它之后。

### 4.1 P0：钱、正确性、安全（约 2–3 周）

**P0-1 成本归因与计费可见性（M）**

- 现状：`usage_events` 只有 `run_id/model/prompt_tokens/completion_tokens`（`services/account-service/account/models/account.py:75-84`）；全仓无价格表、无 `cost_usd`；BYOK 与平台 key 的用量不区分；前端 usage 页只有 token 绝对值（`apps/web/src/pages/usage.tsx:17-121`）。
- 主流：LiteLLM 成本映射、Langfuse generation cost、AgentOps 按 run 成本；SaaS 平台「每个 run 多少钱」是标配（[08a](./08a-market-matrix.md) §1.3）。
- 影响：无法定价、无法给租户看账单、无法定位哪个 run 烧钱；BYOK 与平台额度混在一起，商务上说不清。
- 实现方案：
  1. `services/llm-gateway/llm_gateway/services/pricing.py`：价格表（provider/model/input/output/cached 单价），可用内置映射 + `LLM_GATEWAY__PRICING_FILE` 覆盖；在 completion/stream/embeddings 三路回包时写入 `cost_usd`。
  2. `UsageEvent` 增列：`cost_usd Numeric(12,6)`、`source`（byok/platform）、`step_id`、`phase`（plan/tool/answer）、`conversation_id`；配 alembic 迁移（服务默认 `AUTO_CREATE_TABLES=false`）。
  3. orchestrator 侧重试/多步调用带上 `step_id`；usage 上报幂等（与 P0-3 合并做）。
  4. `GET /v1/usage/summary` 增 `cost_usd` 与预算水位；usage 页加「本月成本 / 预算 %」卡片与按模型成本分布。
- 验收：mock 价格下，一条 run 的明细汇总 = 手算值（误差 <1%）；BYOK 与平台用量分列；usage 页可见 `$` 与超限提示。

**P0-2 对话直答路径的计量与配额（S–M）**

- 现状：`services/agent-orchestrator/agent_orchestrator/services/chat.py:203-252` 直接调模型，不查配额；`services/usage.py:66-76` 无采集器时 `record` 是 no-op；run 的准入在 `run_lifecycle.py:90` 才 `_enforce_quota`（且 fail-open）。**对话是最高频路径，却完全绕过计量闸**——免费无限用 + 账单黑洞，比 06 的描述更严重。
- 主流：每条推理请求都经租户预算/配额准入，超限 402/429 并提示（[08a](./08a-market-matrix.md) §1.2）。
- 实现方案：
  1. 在 `chat.py` 组装请求前调用抽出的 `run_quota.enforce(session, tenant_id, scope="chat")`；回复后 `usage.record`（`run_id=None, conversation_id=...`）。

**P0-3 usage 上报 at-most-once（S）**

- 现状：`services/agent-orchestrator/agent_orchestrator/services/usage.py:125-139` 上报失败只 `warning` 后 return；模型账单与平台用量长期对不上。

**P0-4 多实例正确性：三处锁（M）**

- 现状：① `packages/events/events/outbox.py:119-132` `claim` 只 `select status=PENDING`，无 `with_for_update(skip_locked=True)`；② `services/jobs_worker.py` 领取 job 后有 60s lease（`core/config.py:60`）但**不续租**，长 run 会被第二实例重复领取；③ `services/workspace-service/workspace/services/sandbox.py:525-557` reaper 无领取标记，多副本会重复销毁。jobs 的 SKIP LOCKED 已修（`repositories.py:339-358`），但仍无续租。
- 主流：DB 行锁/SKIP LOCKED + 心跳续租 + Redis 分布式锁（[08a](./08a-market-matrix.md) §3）。
- 实现方案：
  1. outbox `claim` 改 `with_for_update(skip_locked=True)` + 处理中状态（或租约列 `claimed_until`）。
  2. jobs worker 执行期每 `lease/3` 秒续 `lease_expires_at`；心跳丢失即释放，执行结束显式清理。
  3. reaper 用条件更新领取（`UPDATE sandboxes SET reaping_at=now() WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`）。
  4. 新增多 worker 集成测试：真 Postgres（testcontainers）起 2 个 worker 抢同一批 job/事件，断言无重复执行。
- 验收：两副本下同一 job 只执行一次；outbox 无重复投递；reaper 不重复回收；集成测试进 CI。

**P0-5 限流 Redis 化（M）**

- 现状：`services/bff/bff/main.py:67-89` 进程内滑窗；OAuth 动态注册限流同样进程内（`bff/core/config.py:35-37` 注释自认「Redis 在 M0-03 接入」）。

- 验收：两实例共享 Redis 时第 N+1 个请求 429（limit 不翻倍）；Redis 不可用时降级不 500。

**P0-6 MCP server 注册 SSRF 校验 + 工具面降级可观测（S–M）**

- 现状：`services/agent-orchestrator/agent_orchestrator/schemas/mcp.py:45-61` 只校验 name pattern 与 URL 长度，无 scheme/host 校验（可填内网、回环、`169.254.169.254`）；加载失败在 `graph/nodes.py:122-135` 被 `except Exception: extras=[]` 静默吞掉，计划审批据此判断「无危险工具」可能自动放行。对比：`fetch` 与 `file_capture` 已有 SSRF 防护（`services/tool-service/tool_service/services/executors/fetch.py:97/229`、`services/file_capture.py:165-207`），说明这是遗漏而非设计。
- 实现方案：
  1. `mcp_servers.py` 增加 URL 校验器：仅 `http/https`；DNS 解析后拒绝私网/回环/链路本地/元数据地址（防 DNS rebinding，解析与连接用同一结果）；提供 `MCP_ALLOWED_HOSTS` allowlist 开关。
  2. 加载失败落事件 `mcp.tools.load_failed.v1` + 指标 + 告警；计划审批界面标注「工具面不完整」，确认闸口径与执行期一致。
  3. 注册/更新接口的校验错误返回 422 + 明确原因。
- 验收：注册内网 URL 被拒绝；非法 host 不发起连接；加载失败在事件流与 UI 可见。

**P0-7 管理面 RBAC 与审计（S–M）**

- 现状：`services/account-service/account/api/v1/account.py:41-82` 三个写端点（改组织/改成员角色/改套餐）无角色校验；account 服务零 `audit` 命中，事后无法追责。

- 实现方案：
  1. 角色模型：`owner/admin/member`（现在只有 role 字段），写端点校 `owner|admin`；`member` 只读。
  2. `admin_audit_events` 表（actor/action/target/before/after/ip/ua/at）+ 写端点统一落审计 + `GET /v1/admin/audit`（分页、按时间/actor 过滤）。

- 验收：member 调写端点 403；每次管理写操作有审计记录且可导出。

### 4.2 P1：机制代差（约 4–6 周）

> 排序原则：先做「不改 schema 就来不及」的（P1-A/B/D 共用工具/事件决策点），再做产品面（P1-C/E/I）。

**P1-A 工具执行 policy 引擎（L）**

- 现状：审批挂在 run 上（`services/approval.py` 风险分级 + 租户策略表），无「行为级」规则；沙箱边界在 workspace-service（网络/可写路径）、审批边界在 orchestrator，两边各写一份会漂移。
- 主流：Codex 3 档 sandbox × 4 档 approval + Starlark `prefix_rule(allow·prompt·forbidden)` + `host_executable` 路径白名单 + protected paths；Claude Code 分层权限 + 分级模式（[08a](./08a-market-matrix.md) §2.1）。
- 实现方案：
  1. 边界单点定义：`tool-service`（或 `packages/common`）定义 `ExecutionBoundary`（可写路径/网络/受保护路径/shell 前缀），沙箱执行器与 policy 引擎共同消费。
  2. policy 表（租户级）：`{match: {tool, command_prefix, path}, decision: allow|prompt|forbidden, scope: once|session|always, source}`；评估挂在工具执行前（`graph/nodes.py:274-296` 的确认闸之前）。
  3. 决策进事件流：`tool.policy.decision.v1`（rule_id/decision/reason），支撑审计与「为什么这次没问」。
  4. 三级记忆：一次/会话/永久，前端确认卡提供「本次/本会话/总是」；越界 escalation 走既有审批通道。
  5. 与 hooks（P1-B）共用执行前后决策点，避免两套拦截。
- 验收：`rm -rf /` 类命令被 forbidden 直接拒绝；`git status` 在 allow 名单内不再弹确认；决策可在事件流回放。

**P1-B harness hooks（M）**

- 现状：只有 httpx `event_hooks`（`services/llm.py:146-189`、`services/quota.py:76`），无应用级生命周期钩子。
- 主流：Claude Code 5 类 hook 执行器 × 3 档节奏；Cline SDK plugin；行业 145 个大型 OSS 只有 14 个 hooks（[08a](./08a-market-matrix.md) §2.1、[06](./06-refresh-2026-10-25.md) §0）。
- 实现方案：先做 5 个事件（`PreToolUse/PostToolUse/SessionStart/SessionEnd/PreCompact`）；处理器两类（shell / webhook），超时与失败策略（阻断/记录）；hooks 表（租户级、可启停）+ 前端管理页；执行进审计；与 P1-A 共用决策点。
- 验收：配置一个 `PreToolUse` shell 钩子返回非零即阻断工具执行；`PostToolUse` 输出回喂模型；hooks 执行有审计记录。

**P1-C 恢复语义：checkpoint 产品面 + run 超时/优先级（L）**

- 现状：生产 PG checkpointer 已接（`core/container.py:429-465`），但无快照列表/回退/fork；resume 换 thread（`run_execution_approvals.py:208`、`run_execution.py:362`）；retry 建 child run（`:280-343`）；无 `run_timeout_seconds`、无 priority 列。
- 主流：turn 级（Claude Code 每 prompt 自动 checkpoint、留最近 100 个文件快照、`/rewind`）、会话级（Codex resume/fork）、机器级（microsandbox snapshot）三层（[08a](./08a-market-matrix.md) §3 第 4 条）。
- 关键约束：**先定「恢复语义」再定快照载体**——恢复到哪个 turn、产物如何对齐、审批记录是否重放、回退后状态机怎么继续。
- 实现方案：
  1. `GET /runs/{id}/checkpoints`（用 `run_events.seq` 做索引，step↔checkpoint 映射见 07 §S3）。
  2. `POST /runs/{id}/rewind`（fork 新 thread，事件里记 `rewound_from`）；`POST /runs/{id}/resume`（从指定 checkpoint）。
  3. 快照载体分两步：先「逻辑恢复」（事件回放 + 对话/产物引用），再评估文件快照（沙箱侧 diff/快照）。
  4. `runs.timeout_seconds` + 调度器墙钟超时；`runs.priority` + 领取排序。
  5. 前端：run 详情时间线点选回退；超时/优先级在创建表单可设。
- 验收：任一 step 失败可不重跑前序直接回退重试；超时的 run 自动失败并释放并发额度。

**P1-D 事件分类学：thread/turn/item + plan 一等 item（M）**

- 现状：已有事件溯源 + `run.step.v1` + S1 投影，但 plan 仍是消息/文本，事件无 kind 分类。
- 主流：Codex 把 plan/commandExecution/fileChange/mcpToolCall/webSearch 定义成带 started→delta→completed 的 item（[08a](./08a-market-matrix.md) §3 第 4 条）；AG-UI 有 Interrupts/State/Subagents/Reasoning 事件族。
- 实现方案：定义 `run.item.v1`（kind=plan/tool/file_change/mcp_call/search，phase=started/delta/completed，payload 带 step_id）；前端统一 item 渲染器；与 07 的 S2（step 级 token）合并落 step 维度；后续 AG-UI 适配层可直接映射。
- 验收：一次 run 的 UI 能按 item 展开/折叠；plan 修改落新 item 版本；事件可回放重建完整过程。

**P1-E 子代理委派（L）**

- 现状：`parent_run_id` 只用于 retry（`services/run_execution.py:311`），无子 run 委派/子代理工具。

- 验收：子任务在独立 context 完成，父 context 只增摘要；子 run 可取消/超时；UI 可见父子树与各自成本。

**P1-F 上下文工程管线（M–L）**
