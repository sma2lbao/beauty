## 0. 一页结论

1. **主循环已经齐了，缺的是四块地基。** 单 run 闭环（工具 → 审批 → 执行 → 事件 → SSE → UI）、上下文压缩/记忆、技能渐进加载、子代理、模型选择/fallback、沙箱执行（exec/run_code）、Langfuse 观测栈都已落地；剩下的不是「再加一个功能」，而是钱与安全、机制层、工具面长尾、接入形态。
2. **P0 七项已全部落地（P0-1/2/3/6 于 2026-11-09，P0-4/5/7 于 2026-11-10）。** P0-1 把成本从 Langfuse span 搬到 `usage_events`（网关算价 → 编排器透传 → `/usage/summary` 聚合 → 用量页出金额，区分 BYOK/platform、单独统计未计价）；P0-3 把上报改成 outbox 至少一次 + `event_id` 幂等（见 [design/usage-delivery.md](../design/usage-delivery.md)）；P0-2 让对话直答也过月度配额闸并在非流式路径补记用量（失败请求不补记）；P0-6 把 MCP 出站地址收口到 `services/net_guard.py`（私网/元数据/回环/链路本地/保留/组播/CGNAT 全拒，`MCP_ALLOWED_HOSTS` 精确放行）并让工具面加载失败不再静默（见 [design/mcp-security.md](../design/mcp-security.md)）；P0-4 把 outbox claim / job lease / sandbox reaper 三处补成有锁有租约；P0-5 接 `REDIS_URL`，限流可跨副本共享（见 [design/rate-limiting.md](../design/rate-limiting.md)）；P0-7 落管理面 RBAC/审计：`users.role`（不进 JWT，每请求读库）+ `ADMIN_EMAILS` 引导 + append-only `audit_logs`（写动作同事务、denied 独立短线）与 Web `/admin` 管理台（见 [design/admin-plane.md](../design/admin-plane.md)）。
3. **P1 的「机制代差」四项已全部落地（2026-11-10）**：工具 policy 引擎、应用级 hooks、恢复语义、MCP 双栈（P1-H）均已落（参数级规则 + 三档授权见 §5.1 P1-A；五事件 webhook hooks 见 P1-B 与 [design/hooks.md](../design/hooks.md)；run 超时/优先级 + checkpoint 列表/rewind/fork 见 P1-C 与 [design/recovery.md](../design/recovery.md)；`2026-07-28` 无状态栈 + `server/discover` + 客户端 auto 协商见 P1-H 与 [design/mcp-dual-stack.md](../design/mcp-dual-stack.md)）。机制层已无代差；能力层（工具面长尾 / eval / 成本看板）也已在 2026-11-10 补齐（见 §2 #16–#18）；前端原地闭环同批落地（见 §5.2 P1-I 与 [design/interaction-closure.md](../design/interaction-closure.md)）；剩余主要是接入形态（CLI/SDK/headless）与桌面端体验。
4. **工具面长尾两块都落了**：`web_search`（M3，tavily/brave + 出口校验 + 默认关，见 [design/web-search.md](../design/web-search.md)）与后台作业 `job_start/job_output/job_kill`（M2，沙箱常驻进程 + 惰性超时，见 [design/background-jobs.md](../design/background-jobs.md)）均于 2026-11-10 落地；剩余是跨实例持久 shell（M2 后半）与接入形态。
5. **前端/桌面端不缺页面**：原地闭环已于 2026-11-10 补齐（消息复制/重新生成/编辑重发、会话内计划编辑、代码高亮、错误边界，见 §5.2 P1-I 与 [design/interaction-closure.md](../design/interaction-closure.md)）；桌面端仍缺 md/diff/审批渲染与 `shell.run` UI，@引用/斜杠、上下文水位仍缺；对话直答流的中断已收口（客户端重拉已落库内容，不做增量续传，见 §6.2 第 4 条）。

**19. 稳定幂等键（11-17 新落）**：orchestrator 对 WRITE/DESTRUCTIVE 工具生成跨 attempt 稳定的 `orch1:sha256(run_id|node|tool_name|规范化参数)`（`agent_orchestrator/graph/idempotency.py`），经 `ToolExecuteRequest.idempotency_key` 传到 tool-service 的 `tool_calls.idempotency_key`（迁移 `0006_tool_call_idempotency` + 唯一约束 `(account_id, idempotency_key)`，NULL 互不冲突）；查重按键优先、无键回落 `tool_call_id`，同键异参 409。崩溃恢复后模型会重新生成 `tool_call_id`，稳定键不变，已落审计的写副作用因此不会重复执行。**残余**：对话直答 / 确认端点 / MCP 直调三条非图路径不传稳定键；rewind/fork 已有外部副作用台账与显式确认（§2 第 23 条），但没有补偿执行器；同一 run 内同参同工具两次写会被判为一次重放（有意取舍）。当时的两条残余（同键并发各执行一次、崩溃在落库前重试再执行）已由执行期预留收口（§2 第 24 条）。
**20. 崩溃续跑（11-17 新落）**：进程崩溃后 run 会停在 `planning/running` 而 job 事务回滚（`run_events.py` 的 delta/item 投影会提前 `commit`），旧动作重放必 409、重试耗尽后永久挂起（超时 sweeper 默认关）。现在 `services/run_recovery.py::recover_run` 用 `graph.aget_state(thread_config(run))` 取同一线程 checkpoint（attempts 不变）续跑：闸口中断直接补落 `awaiting_approval`/`awaiting_input`、`next` 为空用快照收尾、否则 `ainvoke(None)` 续跑；没有 checkpoint 才退化为新 attempt（`fallback: plan`）。每次恢复落 `run.recovered.v1`。触发两条：worker 对 `plan/approve/confirm/resume` 撞上执行中状态时改道 recover（有 live job 则跳过），新增 `services/run_recovery_sweeper.py` 扫 grace 60s 的孤儿 run 入队 `recover`（配置 `run_recovery_grace_seconds` / `run_recovery_sweep_interval_seconds`）。**残余**：无 fencing（恢复进程与原进程可能各跑一遍）、`awaiting_*` 不恢复（由 interrupt sweeper 兜）、retry 派生子 run 崩溃后停 pending 需人工重跑。详见 [design/recovery.md](../design/recovery.md) §8。
**21. 取消在节点边界真打断（11-17 新落）**：此前 `cancel` 只改库里的 `runs.status`、清排队 job，正在跑的图不知情（用户在界面点取消后模型与工具继续烧）。现在 graph 侧新增 `CancellationPort`（`graph/ports.py`，默认恒假）与 `graph/cancellation.py::raise_if_cancelled`，在节点入口、每轮模型调用前、每次写工具与工具调用前查一次；services 侧 `RunCancellationProbe` 直接查库（跨进程成立），命中抛 `RunCancelled` 并走 `settle_cancelled`（不写 failed、不覆盖 `status_reason`）。**配套的硬约束是节点边界提交**：执行方整段不提交时取消方在 `UPDATE runs` 上拿不到锁（SQLite 库锁/PG 行锁），所以新增 `BoundaryPort` + `SessionBoundary`，`instrument_node` 在每个节点开工前 `commit`。**残余**：粒度是节点边界（长模型/工具调用不劈开）、每边界一次 SELECT、`aupdate_state` 路径无探针。详见 [design/recovery.md](../design/recovery.md) §9。

**22. 步骤实时落库（11-17 新落）**：`run.step.v1` 此前只在一次 `graph.ainvoke` 返回后由 `_step_stream` 统一落库，多节点图（execute→verify→deliver）要等整段跑完前端才看得到「执行步骤」。现在 `graph/steps.py` 的 `StepProjector.flush()` 在每个节点结束（成功/失败/取消都落）后调用，services 侧 `_RunStepSink.flush()` 立刻 `append_event` 并 `commit`；落库故障只记 warning、不把节点判失败（步骤是观测面）。**残余**：只落**已结束**的步骤（running 相位不发事件，避免 `list_steps` 重复计数）；`run.item.v1` 仍在 `ainvoke` 边界落库，节点内部的工具明细仍要等该次图调用返回；未接 `graph.astream`。
**23. 回退前的外部副作用台账（11-17 新落）**：rewind/fork 回退的是图状态，不是世界状态——检查点之后的写工具已经真实改过外部（文件/Notion/消息），重跑时同参调用由稳定幂等键挡住，但**参数变了就是新写**，fork 换 run_id 更是全新键。现在 `services/run_side_effects.py` 把 `run.tool.called.v1` 里 `risk in {write, danger}` 的调用投影成只读台账（失败/超时/interrupt 也算，因为写可能已发生；不新增表），`require_acknowledged` 在 rewind（API 路径）与带 `checkpoint_id` 的 fork 上闸：有写且未传 `acknowledge_side_effects=true` → 409 `run.side_effects_present`（details 带 count/tools/前 20 条明细），确认后把 `side_effects: {count, tools}` 写进 `run.rewind.v1` / `run.created.v1` 载荷供审计；新读端点 `GET /v1/runs/{id}/side-effects`。**残余**：确认只是知会、不是补偿（撤销执行器未做）；台账只覆盖图执行路径；rewind 后改计划导致的新写无法预防。前端（`apps/web` 回退/分叉弹窗）11-17 已接：先列台账、未勾选知悉不能提交，409 明细回填提示。详见 [design/recovery.md](../design/recovery.md) §10。
**24. 写工具执行期预留（11-17 新落）**：稳定幂等键当时只管到「提交期」——两个同键请求可以各自跑完再撞唯一约束，崩溃恰在审计行提交前时重试也会再执行一次。现在 tool-service 在执行前先落一行 `status=running` + `lease_until`（`TOOL__RESERVATION_LEASE_SECONDS`，默认 900s > 单次超时上限 600s）的预留行，执行完更新同一行（迁移 `0007_tool_call_reservation`，新增 `status`/`lease_until`/`cancel_requested`/`result_json`）：**同键且租约未过期 → 409 `tool.call_in_progress`**（details 带 `lease_until`），租约过期或 `abandoned` → 原子抢占（条件式 `UPDATE`）后重跑；终态重放优先回 `result_json` 里的原结果（再叠 `replayed`/`note`），参数不符仍 409 `tool.idempotency_conflict`，已取消行回 `tool.cancelled`。**残余**：无 fencing token（租约到期抢占假定原执行者已死，极端情况两边各执行一次）；沙箱 argv 不打断；三条非图路径仍不传稳定键因而用不上预留；`abandoned` 已建模但暂无写入方。详见 [design/tool-service.md](../design/tool-service.md) §11.1。
**25. 执行期取消（11-17 新落）**：第 21 条的取消只在节点边界问状态，一次卡住的模型/工具外呼会把取消拖到它返回为止。现在 `graph/cancellation.py::guarded(runtime, start)` 把外呼包成 `ensure_future` + `asyncio.wait` 分片等待，每 0.25s 问一次探针，已取消就 `task.cancel()` 并抛 `RunCancelled`；覆盖 `execute` 的 `llm.complete`/`toolkit.execute`、`tool_exec` 的 `toolkit.execute`、`plan_nodes._text_reply` 的 `complete` 与流式每次 `anext`。配套两级协作：`cancel_run` 经 `configure_tool_cancel` 注入的通知器调 `ToolClient.cancel_tools` → `POST /v1/tool-calls:cancel`，把该 run 的 running 行标 `cancel_requested`，tool-service 按 `TOOL__CANCEL_POLL_SECONDS`（0.5s）轮询后放弃等待、落 `status=cancelled` 并回 200 的 `tool.cancelled` 信封。通知是旁路（`NOTIFY_TIMEOUT_SECONDS=2.0`，失败只 warning，不影响取消）。**残余**：沙箱里已起的命令不打断；同步阻塞在事件循环线程里的调用打不断；无 fencing。详见 [design/recovery.md](../design/recovery.md) §9.5。

**26. 子代理异步等待（11-17 新落）**：此前 `spawn_subagent` 在父 run 的 execute 节点内**内联**跑子 run
（`asyncio.create_task` + 每 1s 轮询），父 run 被整体阻塞，子 run 也不进 job 队列，父/子一起崩溃就成孤儿。
现在 `jobs_enabled=True` 时 spawn 只把子 run 的 `plan` 入队并返回 `{pending:true, subagent_run_id}` ack，
父 run 进入新节点 `subagent_wait`（`interrupt({kind:"subagent_wait"})`）落状态 `awaiting_subagent` +
`run.subagent.waiting.v1`；子 run 终态由 `services/subagent_wake.py::notify_parent` 入队 `subagent` job，
worker 调 `services/run_subagent_resume.py::resume_subagent`：子 run 未全终态就收手等下一次，全终态则
`Command(resume=...)` 继续图并把「[子代理结果回执]」作为 user 消息追加进 `tool_history`（spawn 的 ack 已占
`tool_call_id`，补 tool 消息会违反 OpenAI 协议）。三件事必须同时落，因为 `jobs_worker` 只有**一个**消费者：
父 run 若仍占着 worker 等子 run，子 run 的 job 永远没人取（自锁）。**11-18 增补**：初版的两条静默降级已收口
——同回合「待确认写 + spawn」时 `execute` 同时返回 `pending_writes` 与 `pending_subagents`，确认后
`tool_exec` 收下 spawn 的 ack，新增 `route_after_tool_exec` 与改写的 `route_after_confirm`（拒绝写但仍有回执
也去等待节点）把它转回 `subagent_wait`；spawn 被账号审批策略设为 confirm 时走确认闸后同样进等待节点，
不再退化成「子 run 跑完、父 run 收不到回执」。**残余**：子 run 停在 `awaiting_*`
不唤醒父 run。**11-17 增补**：漏唤醒与等待超时已由
`services/subagent_wait_sweeper.py` 收口——子 run 全终态但父 run 无 live job 时重排 `subagent` job
（漏唤醒补偿），仍有在飞子 run 且超过 `subagent_wait_timeout_seconds`（默认 3600s）时逐个 `cancel_run`
（原因「子代理等待超时」）再唤醒父 run；sweeper 只在 `jobs_enabled` 时启动，间隔
`subagent_wait_sweep_interval_seconds`（<= 0 关闭）。**11-18 增补**：超时计时只看**在飞**子 run
（已终态的历史子 run 不再把新子 run 一出生就判超时），且子 run 停在 `awaiting_approval`/
`awaiting_confirmation`/`awaiting_input` 时**不取消、不计时**（等人≠卡住，通知已发到账号；人工
不处理则父 run 一直等，兜底是父 run 的 `run_timeout_seconds`）。详见
**11-18 增补**：会话执行面板在父 run 停在 `awaiting_subagent` 时按 1.5s 轮询
`GET /runs/{id}/subagents` 列出子 run（子 run 有 `conversation_id=None`，会话里看不到它们），
停人工态时明示「等人」；每行「打开」走新增的 `/runs?run=<id>` 深链。详见
[design/subagents.md](../design/subagents.md) §6.1、§6.2、§6.3 与 §10。

**27. 停服兜底（11-18 新落）**：`AppContainer.stop` 原来对 8 个后台任务与每个资源 closer 都是无超时的 `await`，任何一个不响应取消的等待都会让 uvicorn / `TestClient` 关闭无限期挂住（门禁偶发卡在 `with TestClient(app)` 退场的可疑来源）。现在任务清单收敛为 `_STOP_TASKS`，逐个 cancel 后用 `asyncio.wait(timeout=settings.stop_timeout_seconds)`（默认 5s）等退出，closer 包成独立 task 走同一超时；超时只记 `stop timed out` / `close timed out`（带 resource 名）并放手，不再二次等待。详见 [design/recovery.md](../design/recovery.md) §11。**残余**：放弃等待的任务在关闭窗口内仍可能写库；机制未上移到 `common`，其它服务 lifespan 仍是无超时 await。

**28. 会话读模型事件化（11-18 新落）**：会话工作台原先对同一个 run 开四个 1.5–2s 轮询（run 2s、plan/steps/todos 各 1.5s），一个 run 运行中约 2.7 req/s。现在步骤与清单改由 SSE 投影（`apps/web/src/lib/presentation/projections.ts` 的 `stepsFrom`/`todosFrom`），`/steps`、`/todos` 只在 `connected === false` 时回落；plan 去掉轮询、只按 `run.planned.v1`/`run.plan.edited.v1` 失效重取；run 状态由非噪声事件失效，不再 2s 轮询。服务端配套：`events/stream` 新增 `include_steps=1`（默认仍滤掉 `run.step.v1`，审计口径不变）、`sse_poll_interval_seconds` 0.5 → 1.0。运行中页面降至约 0.2 req/s（只剩侧栏 5s；该 5s 已被第 29 条的账号级状态流取代）。详见 [design/event-taxonomy.md](../design/event-taxonomy.md) §11。（抽屉 `/runs` 详情已由第 30 条收口。）**残余**：`/steps`、`/todos` 仍读整份事件表；子代理清单仍 1.5s。

**29. 账号级 run 状态流（11-18 新落）**：第 28 条收口后运行中页面只剩侧栏/看板共用的 `['runs']` 列表 5s 轮询——根因是账号级没有事件源（单 run 才有 `events/stream`，通知流只覆盖审批/终态且只失效 `['notifications']`）。现在新增 `GET /api/v1/runs/stream`（SSE，帧 `run.state.v1`，`id: <updated_at>|<run_id>` 复合游标，首帧 `: ready`，不发 `stream.end`），帧里直接带整份 `RunRead` 摘要；前端 `apps/web/src/lib/runs-stream.ts` 把它 upsert 进 `['runs']` 缓存（未加载时不凭空写入），断线 1s→30s 退避重连带 `Last-Event-ID` 续传，连接状态经 `useSyncExternalStore` 供侧栏（`use-sidebar-model.ts`）与看板（`use-runs-model.ts`）把 `refetchInterval` 从 5000 改成 `connected ? false : 30_000`。服务端 `repositories/run.py::list_changed_after` 按账号 + 复合游标增量查，无游标时从头 60s 变更开始（覆盖「拉列表 → 建流」窗口），游标非法在建流前 400 `sse.bad_cursor`；路由必须注册在 `/{run_id}` 之前（`tests/test_runs_stream.py` 用 OpenAPI paths 顺序钉住）。详见 [design/event-taxonomy.md](../design/event-taxonomy.md) §12。**残余**：扫描式推送不是事件总线（1s 级延迟，`runs.updated_at` 无索引）；每标签页一条连接（可用 `BroadcastChannel` 复用）；半开连接只能靠 30s 兜底纠正；通知流仍保留（toast/通知中心职责不同）。

**30. 详情抽屉读模型事件化（11-18 新落）**：第 28 条把会话页收敛后，`/runs` 详情抽屉仍对同一 run 开着 6 个 1.5–2s 轮询（run 2s、steps/items/todos/subagents/usage 各 1.5s）。现在抽屉也改「投影优先、断线回落」：`useRunEvents(runId, { includeSteps: true })` 取流，`apps/web/src/lib/presentation/projections.ts` 新增 `itemsFrom`（与服务端 `items.py::list_items` 同规则折叠：`item_id` 首现定序、相位取最新、`data` 浅合并）、`lastUsageEventSeq`、`lastSubagentEventSeq`；`steps`/`items`/`todos` 由事件派生，`/steps`、`/items`、`/todos` 只在 `connected === false` 时回落（1.5s，终态即停）；`subagents` 只在 `awaiting_subagent` 且断线时 1.5s；`usage` 去轮询、按 `run.usage.v1` 失效；run 状态按非噪声事件失效（连上时不再 2s 轮询）；`ended` 收尾统一失效八项。结果连上时抽屉对同一 run 零轮询。详见 [design/event-taxonomy.md](../design/event-taxonomy.md) §13。**残余**：客户端折叠规则需与服务端保持同步（测试只对拍字段层）；断线回落的三个端点仍读整份事件表；checkpoints/side-effects/artifacts 仍按需拉取。

**31. 会话沙箱 scope_key 前缀前后端不一致（11-18 修复）**：会话页「文件 / 终端」两个页签一直显示「这个会话还没有运行中的沙箱」——不是沙箱没起，而是查不到：`apps/web/src/lib/sandbox-api.ts` 的 `conversationSandbox()` 用 `conv:<conversation_id>` 过滤，而写入方一直是 `conversation:<conversation_id>`（`services/tool-service/tool_service/services/sandbox.py` 的 `SCOPE_CONVERSATION_PREFIX`、`services/agent-orchestrator/agent_orchestrator/context/sandbox_files.py` 同值）。该分叉自 2026-10-25 首版就存在（tool-service `fde652a` 写 `conversation:`、web `267e196` 写 `conv:`），workspace-service 只做存储不校验格式因此一直没有报错，前端单测夹具也用 `conv:` 自洽，所以没人发现；本地 Postgres `sandboxes.scope_key` 实查全是 `conversation:*`。现在前端抽出 `conversationScopeKey()` 显式对齐 `conversation:`，并加一条钉住 `?scope_key=conversation%3A<id>` 的回归测试；文档 [design/tool-service.md](../design/tool-service.md) §8.1 的 5 处 `conv:` 统一成 `conversation:` 并加跨服务契约提醒。**残余**：scope_key 仍是纯字符串约定（无共享常量、无跨语言契约测试），再改前缀仍会两侧失联；沙箱闲置（`TOOL__SANDBOX_TOOL_TTL_SECONDS=1800`）被回收后会话页也只显示「没有运行中的沙箱」，未区分「跑过但已回收」与「从没跑过」。

### 4.2 逐项现状与做法

- **P0-1 成本归因 ✅**：已按「网关单源计价 → 编排器透传 → `usage_events` 落库 → `/usage/summary` 聚合 → 用量页出金额」落地，详见 [design/cost-attribution.md](../design/cost-attribution.md)。要点：价目表复用 litellm 本地表（含缓存价）不新造 `pricing.py`；`usage_events` 加 `cost_usd`（NULL=未计价）与 `billing_source`（platform/byok）；未计价调用单独计数而不是按 0 元吞掉。**残余**：`step_id/phase` 维度拆分、BYOK 调用审计、金额随 usage 的可靠投递（属 P0-3）。
- **P0-2 对话配额闸 ✅**：对话直答此前只在流式路径上报 `run_id=None`，非流式 `chat.answer` 不记，且 chat 完全绕过 run 准入的双重判定。现已落地：`run_quota.enforce_monthly_quota(account_id)` 抽成公开月度闸（月度 token 用尽抛 429 `quota.monthly_tokens_exceeded`；快照取不到时仍 fail-open），非流式与流式两个入口都在**调模型之前**执行（流式必须在 `StreamingResponse` 之前，SSE 一旦 200 就不能改状态码）；对话不占 `max_concurrent_runs`（那是 run 的维度）。非流式 chat 现在包 `UsageCollector` 边界，答案落库后经 `post_commit.register_after_commit` 在提交后上报 `run_id=None`（不在请求事务里直接 report：outbox 会另开写连接与未提交事务抢 SQLite 单写锁）；没有 post-commit runtime 的直调退回同步上报。account 新增会话鉴权的 `GET /v1/usage/quota/me`，Web 用量页有本月配额进度条与剩余量，composer 在收到 429 `quota.*` 时就地提示。**残余**：失败请求已经烧掉的 token 不补记（与提交语义一致）；对话只判月度、不占并发名额；配额只能由服务端维护 `users.quota`，无自助改与预算阈值通知。
- **P0-3 用量可靠投递 ✅**：`UsageReporter.report` 现在先把 `usage.report.v1` 写进编排器自己的 outbox（独立短事务，与 run 事务解耦），dispatcher 经进程内总线投给 `UsageDeliveryConsumer`，逐条 POST 带 `event_id="<outbox id>:<样本序号>"`；account 按 `(account_id, event_id)` 唯一约束幂等，重投返回同一条。入队失败退回旧的逐条直连（best effort），未装配 `session_factory` 的部署行为不变；开关 `usage_outbox_enabled`。详见 [design/usage-delivery.md](../design/usage-delivery.md)。**残余**：outbox claim 无 `SKIP LOCKED`/租约、总线仍是进程内，多副本要等 P0-4；account 侧 failed 投递缺本服务告警（orchestrator 的 `outbox_failed` 只覆盖编排器自己的 outbox）。
- **P0-4 多实例 ✅**：job claim 早已 `SKIP LOCKED`，本次补齐三处：outbox `claim` 在 PG 下 `FOR UPDATE SKIP LOCKED` 且命中行 `available_at=now+lease`（租约到期可重领）；worker 心跳每 `min(lease/3,30)` 秒 `renew_lease`，续租与收尾都校验 `status=running + locked_by=worker_id`，丢锁即停止续租并跳过 finalize；sandbox reaper 改为 `claim_expired` 原子领取（同事务把 `expires_at` 推后 300s）→ 事务外 destroy → 短事务回写，失败只在仍持租时推后 `retry_delay`。**残余**：SQLite 下极端多进程仍可能重复 destroy（PG 无此问题）；跨实例事件投递仍是每实例 dispatcher + 进程内总线（依赖消费幂等）。
- **P0-5 限流 Redis 化 ✅**：`common.security.build_rate_limiter` 按 `REDIS_URL` 选后端——未配 → 原进程内滑动窗口（行为不变）；配了 → Redis 固定窗口（`INCR`+`EXPIRE` 事务 pipeline，键 `namespace:bucket:key`，TTL=2×窗口），多副本共享计数；Redis 故障 fail-open + 结构化 warning（可用性优先）。api-gateway（/api 120/min）与 account（OAuth 动态注册 10/h）已接，compose 默认注入 `*__REDIS_URL`。**残余**：固定窗口边界最多 2× 瞬时；无集群/Sentinel（单点故障即降级为不限流）、无命中/拒绝指标、无路由级或套餐差异化配额；未配 REDIS_URL 的多副本仍各记一份。
- **P0-6 MCP 出站 SSRF ✅**：此前注册只校验 `http(s)://` 前缀，服务端直连用户填的 URL；同仓 `fetch/file_capture` 有私网防护而 MCP 没有；自动加载失败还静默吞异常。现已落地（详见 [design/mcp-security.md](../design/mcp-security.md)）：`services/net_guard.py` 作为出站校验单一真源（私网/回环/链路本地/保留/组播/未指定/CGNAT、IPv4 映射归一；`socket.getaddrinfo` 走 `asyncio.to_thread`），`MCPClient._post` 在首次发包前 memo 校验一次（覆盖 initialize/list/call 与 `/test`），命中抛 `BlockedTargetError`；`MCP_ALLOWED_HOSTS`（host 精确匹配）给自建内网开口子；`schemas/mcp.py` 注册期对字面 IP/localhost 名零网络快速拒绝；`file_capture` 改为共用同一判定函数（下载路径解析失败仍拒绝，MCP 路径放行让连接自己报错）。工具面降级不再静默：`graph/nodes/toolkit.py` 的 `_load_toolkit` 失败留 `logger.warning`（带 account_id 与错误），手动 `/test` 照旧落 `last_status/last_error`。**残余**：校验与真正连接是两次 DNS 解析，仍有 rebinding TOCTOU 窗口（未做 connect 到已校验 IP）；注册期不做 DNS 预校验；出站拦截只有日志没有指标；多副本各自读配置。
- **P0-7 管理面 RBAC/审计 ✅**：此前只剩 `/me` 与 sessions，User 无 `role`，全仓无 `/admin`、无 audit 表。现按 [design/admin-plane.md](../design/admin-plane.md) 落地：
  - **唯一角色源在库里**：`users.role`（`user`/`admin`，迁移 `f2c7b9d4a1e6`，存量回填 `user`）；角色**不进 JWT**，`require_admin` 每请求读库（`api/deps.py`），提权/降权/停用立即生效；`ADMIN_EMAILS` 只做引导（注册/登录持久化 admin、鉴权兜底放行，只升不降）。
  - **管理 API**：`/v1/admin/accounts`（q/status 过滤 + 分页 + 本月用量聚合，单条 group by 避免 N+1）、`/v1/admin/accounts/{id}`、PATCH `quota`（省略保持/`null` 清除/至少一键）、PATCH `role`（改自己 409 `admin.self_role`）、PATCH `status`（停用自己 409 `admin.self_disable`，停用同事务吊销全部 refresh token 与 sessions）、`/v1/admin/audit-logs`。
  - **审计**：`audit_logs` append-only（仓储只 add/list/count）；三个写动作与业务**同事务**落 before/after；无权限访问先落 `admin.access.denied` 独立短事务再 403（失败只 warning，不改变结论）；带 `request_id`/`ip`/`user_agent`，读端点不审计。
  - **前端**：`/admin` 管理台（账号/审计两页签、配额弹窗、角色/状态确认），入口只按 `me.role` 为 `admin` 显示（桌面/移动/命令面板统一过滤），401/403/错误态不白屏。
    **残余**：admin 无细粒度 scope（P1-A 后再考虑）；停用后旧 access token 最长 1h 仍可访问普通端点；审计无链式签名/防篡改（DBA 可改）；读操作不审计；`X-Forwarded-For` 仅在可信代理后可信。
