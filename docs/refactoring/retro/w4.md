## 3. 做对了什么

1. **先定序再并行**：R-39a（源码）与 R-40（conftest/metrics）都动 AO 包，先派 R-40 的 import 侧、再派拆分，并在提交时按「先 R-40 后 R-39a」切分，避免了 run_execution.py 的交织冲突。
2. **纯搬移 + 门面 as 自别名**：10 个源文件拆分零逻辑改动，monkeypatch 目标（`mcp_service.build_client` 等）靠再导出保持，398 例与 golden 9/9 全程绿。
3. **注入验证**：check-workspace.sh 初版第 2 查因 `parent.parent` 条件恒真而永过，是注入违规后才暴露——规则类脚本必须证明「能红」。
4. **门禁先落地再宣称**：R-34/R-35 收口时把 check-versions / allowlist / compose config / release --dry-run 全部实跑贴 EXIT，而不是只写「已接线」。
5. **体量与发布解耦**：R-39 拆文件与 R-34 版本统一互不阻塞，时间盒内 5 项并行完成（09:20 开工，09:55 已完成 5/7）。

## 4. 教训

1. **队员长时无落盘要立刻干预**：w0-ci 在 R-34/R-35 最后阶段停摆 ~20 分钟（本地跑不通 pip-audit 却没上报），lead 用 interrupt + 时间盒指令才收口。规则：单个子任务超过时间盒一半仍无落盘 → interrupt，改为「先交已完成部分 + 明确阻塞点」。
2. **共享工作树里 git 命令仍要限定 path**：本轮 lead 全程按文件清单 `git add`，避免了把其他人半成品带进提交；一旦 `git add -A` 就会把 w0-ci 中途的非法 pyproject 一起提交。
3. **任务上限 8 人导致复用调度成本上升**：本波 7 项只能复用老队员，需要提前把 write scopes 写到文件级（run_execution.py 之争即例证）。
4. **CI 新 job 必须真跑一次**：W2 的「CI 假绿」教训在本波再次生效——security-audit / docker-build 只能在 push 后确认，报告里必须留「待回填」而不是先勾 ✅。
5. **版本类改动要同时锁三处**：pyproject / package.json / uv.lock+package-lock 必须用包管理命令重生成，且 check-versions.sh 只读断言，不再手工 sed。
