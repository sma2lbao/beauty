## 1. 问题与证据（2026-10-25 实测）

### 1.1 发布流程缺失（R-34）

- 18 处版本字段四种取值：根 package.json `0.0.0`、apps 三个 `0.0.0`、packages/design 与 packages/console-ui 与 tools/eslint-config `0.0.1`、根 pyproject `1.0.0`、3 个 Python 库 + 7 个服务 `0.1.0`。
- 0 个 git tag（`git tag | wc -l` = 0），无 CHANGELOG（`ls CHANGELOG*` 空），无 docs/release.md。
- nx 23.2.1 自带 `nx release`（version/changelog/publish 子命令可用），无需新依赖。
- 提交历史 213 条，主体已符合 conventional commits（如 `docs(refactoring):`、`refactor(web):`、`fix(ci):`）。

### 1.2 无安全扫描（R-35）

- `.github/dependabot.yml` 仅 3 个 ecosystem 的周更（github-actions / npm / pip，npm+pip limit 5），无分组、无 assignee、无版本更新策略说明。
- CI 7 组 job 无安全扫描（.github/workflows/ci.yml：setup/docs-check/affected-js/python-lint/python-test/lock-check/alembic-check）。
- `npm audit` 必须显式指定 npmjs registry：默认 registry 是 npmmirror，audit 端点返回 `404 [NOT_IMPLEMENTED] /-/npm/v1/security/*`；`--registry=https://registry.npmjs.org` 实测可用。
- 实测漏洞面：全量 **35 个（17 high / 18 moderate）**；`--omit=dev` 后 **3 high**（zod / zod-validation-error / eslint-plugin-react-hooks 链路，多为无 fix 的 dev 工具传递依赖）。硬性 `--audit-level=high` 全量门禁会永久红，必须区分生产依赖与 dev 工具。
- 本机 pypi.org 不可达（curl 000）→ pip 侧漏洞扫描只能在 CI 验证；`uvx` 0.11.26 可用。

### 1.3 容器化几乎为空（R-36）

- `git ls-files | grep -i dockerfile` = 0；deploy/docker-compose.yml 只有 postgres + redis，无应用服务、无迁移作业、无 app healthcheck。
- deploy/web/nginx.conf 只监听 80，无 TLS、无 `/healthz` `/readyz` location（请求会落到 SPA 的 `try_files /index.html`）。
- deploy/web/README.md 停在 M0-01（写着「BFF 只有 /api/health」），未覆盖 7 服务、迁移、TLS。

## 2. 目标与非目标

目标（W4 出口）：发布可重复（一条命令出 changelog+tag，版本单一真源）；安全扫描进 CI 且可运维；容器化可 `docker compose up` 跑通全栈（CI 至少构建镜像成功）；7 服务探针契约与外部可达一致；体量到 ≤500；W3 移交的接线全部收口；工作区卫生有自动检查。

非目标：

- 不做产品功能与 UI 改版（R-26 视觉差异留人工核对，不在本波改样式）。
- 不切发布渠道（npm/PyPI 发布不启用，仓为私有；`nx release` 只做 version+changelog+tag，`publish` 显式跳过）。
- 不定 SLA/SLO 与告警平台接入（只在文档与探针层面就绪）。
- 不动 desktop main/preload 运行时（含 agent.ts 760 行）；不做 web 剩余 4 文件的拆分（列为可选）。
- 不引入 GitOps/Argo、不写 Kubernetes manifest（单机 compose + nginx 是既定部署单元）。

## 3. 方案

### R-34 发布流程（owner w0-ci）

- 版本策略：**全仓单一版本 `0.1.0`**（root package.json、6 个 workspace package、根 pyproject、10 个 Python 成员统一；发布单元 = 整仓，tag `v0.1.0`）。pre-1.0 阶段允许破坏性变更，minor 即 breaking。
- nx.json 增 `release` 配置：`projects: ["*"]`、`conventionalCommits: true`、`git.tag: true`、`changelog: { workspaceChangelog: true }`、`version.git.tagPrefix: "v"`、`version.conventionalCommits: true`、不配置 publish。
- 新增 docs/release.md：版本策略、发版步骤（`npx nx release` dry-run → 正式 → push tag）、CHANGELOG 约定、回滚（回退 tag 与 version commit）。
- 新增 `scripts/check-versions.sh`：断言 18 处版本全部等于 `0.1.0`、CHANGELOG.md 存在且含 `## 0.1.0` 段、`nx.json` release 配置存在；非 0 退出。
- 首版 CHANGELOG 由 `npx nx release changelog 0.1.0 --from=$(git rev-list --max-parents=0 HEAD)` 生成（213 提交），人工补一行「初始正式发布」摘要。
- 版本字段改动会牵动 uv.lock（workspace 成员版本）与 package-lock.json（workspace 版本）→ 必须用 `uv lock` / `npm install --package-lock-only` 重新生成，禁止手改。

### R-35 依赖更新与安全扫描（owner w0-ci，与 R-34 同人避免 ci.yml 冲突）

- `.github/dependabot.yml`：保留 3 ecosystem，补分组（`dev`/`prod`）、`labels`、`commit-message` prefix；注释写明「只自动更 patch/minor，major 手工」。
- CI 新增 job `security-audit`（needs setup）：
  - JS：`npm audit --omit=dev --registry=https://registry.npmjs.org --audit-level=high` 作为**阻断**门禁（生产依赖必须 clean）；全量审计另起一条非阻断步骤，报告作为 artifact。
  - Python：`uv export --format requirements-txt --no-hashes > /tmp/req.txt && uvx pip-audit -r /tmp/req.txt --disable-pip`（CI 有网络；本地 pypi 不通，只能 CI 验），生产依赖漏洞阻断。
  - 允许清单 `security/audit-allowlist.json`：每条形如 `{ "id": "GHSA-...", "ecosystem": "npm", "reason": "...", "owner": "lead", "expires": "2026-12-31" }`；`scripts/check-audit-allowlist.cjs` 校验过期条目 → 过期即失败。
- 新增 docs/security.md：漏洞处置流程（发现→评估→修复/允许清单→复盘）、允许清单规则、扫描范围说明。
- 当前 3 个生产面 high（zod 链）先尝试 `npm audit fix` / 升级 eslint-plugin-react-hooks；确实无 fix 的进允许清单并设 2026-12-31 到期。

### R-37 探针统一（owner w0-gate，先于 R-36）

- bff 补 `/readyz`：BFF 无 DB，就绪 = 关键配置完整（`AUTH_MODE` 合法、session/JWT 密钥非空）+ 可选上游探测（默认关闭，`READY_PROBE_UPSTREAMS=false`），避免级联判定；响应体与 service_kit 一致。
- 7 服务探针契约测试统一：`/healthz` 200 `{"status":"ok"}`、`/readyz` 200 `{"status":"ready"}`、依赖故障 503；bff 单测覆盖配置缺失 → 503。
- deploy/web/nginx.conf：新增 `location = /healthz`、`location = /readyz` 反代 `bff_upstream`（不走 SPA 回退）；补 TLS 段（`listen 443 ssl`、`ssl_certificate`/`ssl_certificate_key` 路径注释、80→443 跳转），默认注释掉以免本地裸跑需要证书。
- docs/observability.md §探针行改为「7 服务（含 bff）均实现」，并补 bff 就绪语义说明。
- 验收：7 服务进程内测试全绿；`grep -c "get("/healthz")"` 与 `readyz` 计数与实现一致；nginx 用 `docker compose config` 与配置审阅验证（本机无 nginx 二进制）。

### R-36 容器化（owner audit-ops，依赖 R-37）

- deploy/web/README.md 重写：镜像构建命令、compose up、TLS 证书挂载（自签与 certbot 两条路）、迁移顺序、裸机 vs 容器、回滚（回退镜像 tag + 迁移 expand-contract 不回滚）。

- 验收：`docker compose -f deploy/docker-compose.yml config` EXIT 0；CI docker-build job 绿；deploy/README 覆盖 TLS/迁移/回滚。

### R-38 工作区卫生（owner w0-docs）

## 8. 风险与回滚

| 风险                                | 影响                     | 缓解                                                                                           |
| ----------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------- |
| 版本统一牵动 uv.lock / package-lock | 锁文件大 diff、sync 失败 | 只用包管理命令重生成；先改版本再 `uv lock` + `npm install --package-lock-only`；失败回滚该提交 |
| audit 门禁被既有漏洞卡死            | CI 永红                  | 阻断面只覆盖生产依赖；无 fix 的进允许清单（带到期日）；全量报告非阻断                          |
| R-39 拆分破坏 monkeypatch 目标      | 大批测试失败             | 门面 `as` 自别名 re-export（W3 已验证）；每次拆完立刻跑 pytest；按文件独立提交                 |
| 拆分误改逻辑                        | 行为漂移                 | 纯搬移 + golden 9/9 + pytest 计数不减；每文件独立提交可 revert                                 |
| Docker 构建在 CI 超时               | 门禁慢                   | 只构建 bff + web 两个镜像；缓存 BuildKit                                                       |
| env.py 改造打乱迁移                 | 生产库升级失败           | 不改 versions/；改造后 `alembic upgrade head` + `alembic check` 双验；PG 集成测试兜底          |
