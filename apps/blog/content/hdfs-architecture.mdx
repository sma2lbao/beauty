> 本文参考 Apache Hadoop 3.5.0 的 [HDFS Architecture](https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html) 整理，并结合常见运维问题做补充。

## HDFS 解决什么问题

HDFS（Hadoop Distributed File System）的目标很明确：在廉价、会故障的机器上，存下超大文件，并提供高吞吐的顺序读写。

它做了几个关键取舍：

- **一次写入、多次读取**：不适合频繁修改文件内容；
- **大文件友好**：块按 128 MB 量级切分，减少元数据压力；
- **移动计算而不是移动数据**：尽量让计算任务跑在数据所在节点；
- **故障是常态**：副本、校验和、自动恢复都是一等公民。

这些取舍决定了 HDFS 的适用边界：离线批处理、日志归档、数据湖底座很合适；低延迟随机读写、海量小文件、频繁原地更新则不合适。

## 主从架构：NameNode 与 DataNode

HDFS 是典型的 master/slave 架构：

```text
Client
  │  元数据操作（创建、打开、重命名）
  ▼
NameNode（命名空间、块映射、副本策略）
  │
  ├── DataNode A（块 1、块 3）
  ├── DataNode B（块 1、块 2）
  └── DataNode C（块 2、块 3）
```

- **NameNode** 管理文件系统命名空间（目录树、文件到块的映射）和块映射（每个块在哪些 DataNode 上）。它不承载用户数据流。
- **DataNode** 负责实际存储块，按 NameNode 的指令创建、删除、复制块，并定期发送心跳和块报告。
- **Client** 先向 NameNode 要元数据，再直接和 DataNode 传输数据。

这种设计把元数据与数据分离，NameNode 的内存成为集群规模的关键约束。一个文件被切成多少块、有多少小文件，都会转化为 NameNode 的元数据开销。

## 块、副本与放置策略

文件写入 HDFS 时会被切成固定大小的块。Hadoop 3.x 常见的默认块大小是 128 MB（由 `dfs.blocksize` 控制，以集群配置为准）。块大的好处是减少寻址和元数据开销，坏处是最后一个块可能浪费空间，且小文件问题更突出。

每个块默认有 3 个副本（`dfs.replication`）。副本不是随便放的，HDFS 需要考虑机架感知：

1. 如果客户端本身是 DataNode，第一个副本写在本地；否则在同机架随机选一个节点；
2. 第二个副本写到另一个机架的节点；
3. 第三个副本写到第二个副本所在机架的另一个节点。

这样即使整机架断电，数据仍然可用；同时读取时可以优先选择同机架副本，减少跨机架带宽。

副本因子不是越高越好。3 副本意味着 3 倍存储成本，但能容忍两副本同时故障；对冷数据可以降低副本或使用纠删码，对热数据则要保证足够的冗余。

## 写入链路：客户端只负责发，管道负责复制

一次 `create` 写入大致经历以下步骤：

1. Client 向 NameNode 请求创建文件，NameNode 检查权限、父目录和是否已存在，返回成功；
2. Client 请求第一个块的位置，NameNode 返回一组 DataNode（按副本放置策略排序）；
3. Client 与第一个 DataNode 建立连接，第一个 DataNode 再连接第二个，第二个连接第三个，形成复制管道；
4. Client 把数据切成 packet 发送给第一个 DataNode，管道逐级转发；
5. 每个 DataNode 收到 packet 后写入本地，并返回 ack，ack 沿管道反向回到 Client；
6. 一个块写完后，Client 请求 NameNode 分配下一个块的位置，重复上述过程；
7. 所有块写完，Client 关闭文件，NameNode 提交元数据。

这条管道的关键点是：**Client 不直接写所有副本**。它只和管道头交互，复制由 DataNode 完成。这样客户端带宽不会成为副本复制的瓶颈。

如果管道中有 DataNode 失败，Client 会收到异常，HDFS 会尝试从管道中移除故障节点、重新建立管道，并保证已确认的数据不丢。具体行为受 `dfs.client.block.write.replace-datanode-on-failure` 等配置影响。

## 读取链路：就近读取 + 校验和

读取时：

1. Client 向 NameNode 请求文件的块位置；
2. NameNode 返回每个块所在的 DataNode 列表，按与客户端的网络距离排序；
3. Client 选择最近的副本，直接向 DataNode 读取；
4. 读取过程中校验 checksum，发现块损坏会向 NameNode 报告，并尝试其他副本；
5. 读完一个块再读下一个，直到文件结束。

HDFS 默认在写入时计算校验和，读取时验证。DataNode 也会定期做块扫描（block scanner），发现损坏副本后由 NameNode 触发重新复制。

## NameNode 的持久化：EditLog、FsImage 与 Checkpoint

NameNode 的元数据不能只放在内存里，否则重启就丢。它使用：

- **FsImage**：某一时刻的命名空间快照；
- **EditLog**：自上次快照以来的所有元数据变更；
- **Checkpoint**：SecondaryNameNode 或 Standby NameNode 定期合并 FsImage 与 EditLog，生成新的 FsImage，避免 EditLog 无限增长。

注意 SecondaryNameNode 不是热备，它只做 checkpoint，不接管故障。真正的 HA 需要 Active/Standby 两个 NameNode，共享 EditLog（通常是 QJM，JournalNode 集群），并由 ZKFC 做故障切换。

## HA 与 Federation

**HA（高可用）** 解决 NameNode 单点问题：

- 两个 NameNode，一主一备；
- 共享 JournalNode 集群保存 EditLog；
- ZKFC 监控健康状态，主节点故障时切换；
- DataNode 同时向两个 NameNode 发送块报告；
- Client 通过 nameservice 逻辑名访问，不直接绑定某台机器。

**Federation（联邦）** 解决单 NameNode 命名空间和内存上限问题：

- 多个 NameNode，各自管理一个命名空间（namespace）；
- 每个 namespace 有独立的块池（block pool）；
- DataNode 同时为多个块池存储数据；
- 通过挂载表（mount table）把多个 namespace 拼成一棵树。

HA 和 Federation 解决的是不同问题：前者是可用性，后者是扩展性。生产集群经常同时使用。

## Safemode：启动时的保护期

NameNode 启动后会进入 Safemode：

- 不接收写操作；
- 等待 DataNode 上报块报告；
- 当达到最小副本比例（`dfs.namenode.safemode.threshold-pct`）后自动退出。

Safemode 是保护机制，不是故障。集群刚启动、DataNode 还没全部上报时，看到 Safemode 是正常的；如果长时间不退出，通常是 DataNode 没起来、块丢失或阈值配置不合理。

## 常见故障与排查

| 现象                 | 可能原因                               | 排查方向                                            |
| -------------------- | -------------------------------------- | --------------------------------------------------- |
| 写入很慢             | 管道中某个 DataNode 慢、跨机架带宽不足 | 看 DataNode 磁盘/网络、`dfs.datanode.data.dir` 负载 |
| 读取报 checksum 错误 | 磁盘坏块、副本损坏                     | `hdfs fsck`、查看 DataNode 日志、触发重新复制       |
| NameNode 重启很慢    | EditLog 太大、块报告太多               | 检查 checkpoint、FsImage 大小、小文件数量           |
| 副本不足             | DataNode 下线、磁盘满                  | `hdfs fsck`、`hdfs dfsadmin -report`                |
| 大量小文件           | 上游写入策略不当                       | 合并文件、使用归档、调整分区粒度                    |

常用命令：

```bash
# 查看文件与块信息
hdfs fsck /warehouse/orders -files -blocks -locations

# 查看集群容量与 DataNode 状态
hdfs dfsadmin -report

# 查看副本因子
hdfs dfs -stat "%r %n" /warehouse/orders/part-00000

# 手动设置副本
hdfs dfs -setrep -w 3 /warehouse/orders
```

## 小文件为什么是大问题

HDFS 的元数据常驻 NameNode 内存。每个文件、每个块、每个副本都会占用元数据。大量小文件会带来：

- NameNode 内存压力；
- 启动时块报告和 fsimage 加载变慢；
- 查询时打开大量文件，Listing 和任务调度开销上升；
- 每个小文件对应一个任务，调度成本远大于计算成本。

治理思路：

- 写入前合并：按时间窗口攒批，而不是一条一条写；
- 分区粒度合理：不要按小时/用户产生过多小分区；
- 使用表格式的 compaction：Iceberg、Hudi 等可以合并小文件；
- 离线归档：对冷数据使用 HAR 或对象存储归档层。

## 什么时候不该用 HDFS

- 需要低延迟随机读写（用 HBase、ClickHouse、对象存储 + 索引）；
- 需要频繁原地更新（用表格式或数据库）；
- 单文件大量小文件（先治理，不要硬扛）；
- 团队没有运维能力（云上对象存储 + 托管元数据更省心）。

## 练习

1. 用 Docker 启动一个单节点 HDFS，写入一个 300 MB 文件，观察它被切成几个块；
2. 把副本因子设为 2，再设为 3，用 `hdfs fsck` 对比；
3. 手动停掉一个 DataNode，读写文件，观察客户端行为；
4. 写入 1000 个 1 KB 小文件，观察 NameNode 内存和 `fsck` 输出；
5. 画一次写入管道，标出 packet、ack 和故障重试的位置。
