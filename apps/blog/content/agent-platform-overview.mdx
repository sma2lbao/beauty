> 本文是「Agent 平台实现」系列第 1 篇。所有内容都从一个真实在跑的 monorepo（beauty-moon）里提取，不是纸面设计。

## 先想清楚：Agent 平台难在哪

搭一个 Agent 平台，难点不在「调模型 API」——那是最简单的部分。真正的工程挑战是四件事：

1. **长任务**：模型一次调用 3 秒，任务一次跑 3 分钟，HTTP 层、进程生命周期都要为它重新设计；
2. **副作用控制**：让模型调用工具、执行代码、写外部系统，出错的代价是真世界的后果，需要审批、确认、风险分级一整套闸门；
3. **过程透明**：任务跑几分钟，用户要看得到过程、断网要接得回来；
4. **多租户边界**：账号之间的数据、凭证、工具面必须严格隔离。

下面按「需求 → 拆分 → 流量 → 数据 → 选型 → 部署」的顺序，给出一套已经落地的答案。

## 第一步：从产品形态倒推组件

先看产品要什么。一个 to C 的 Agent 平台（对标 Manus / Devin / ChatGPT Tasks 的混合体），用户能感知的功能至少有：

- **会话对话**：发消息，模型流式回答，简单问题直接答；
- **复杂任务**：规划、执行、验收、交付产物，过程可见、可审批、可取消；
- **知识库**：上传文档，Agent 能「先查资料再回答」；
- **连接器**：接 GitHub、Notion 等外部系统（OAuth 授权、凭证托管）；
- **账号**：注册登录、配额、用量统计、API Key；
- **工作区与沙箱**：交付物存放、受控代码执行。

每个功能背后都是一个独立的技术域：流式编排、事件溯源、任务队列、OAuth 生命周期、RAG、认证体系、沙箱隔离。**这就是服务拆分的雏形——按技术域和变更节奏拆，而不是按 HTTP 路由拆。**

## 第二步：服务拆分

真实方案是八个 Python 服务加三个共享库：

```text
浏览器
├── app.example.com          Nginx 托管 SPA 静态产物
│      └── /api/*            FastAPI 网关 :8007（同域反代）
│            ├── 登录/登出/会话 Cookie（account-service 为 IdP）
│            ├── 代理短请求与短流
│            └── 限流/错误契约
└── 长流直连                  SSE，网关只发短时 stream token

应用机（容器编排）
├── agent-orchestrator :8002  会话/run 编排、LangGraph 执行图、审批、事件流
├── tool-service       :8008  内置工具目录/执行/审计（沙箱经 workspace 执行）
├── llm-gateway        :8003  模型唯一出口：白名单/路由/降级/用量
├── connector-service  :8004  OAuth 授权会话/凭证加密/连接生命周期
├── workspace-service  :8005  工作区/交付物/沙箱生命周期/对象存储
├── knowledge-service  :8006  知识库：分块/嵌入/检索
└── account-service    :8001  账号/会话/配额/自建 IdP（JWKS）

基础设施机
├── PostgreSQL 15            每服务独立库（生产）
├── Redis                    限流/锁/短期缓存
└── sandboxd                 gVisor + Docker 沙箱
```

拆分判据可以总结成一张表：

| 判据 | 归属 |
| --- | --- |
| 有独立 Dockerfile、独立数据库、独立迁移节奏 | `services/`（部署单元） |
| 被 import 的代码，不部署 | `packages/`（库） |
| 人直接使用的终端 | `apps/`（SPA / Next.js 官网 / Electron） |

三个 Python 共享库是整套架构的地基：

- **common**：统一错误模型（`AppError` 基类 + `code/message/details` 契约）、配置基类、结构化日志、JWT/JWKS 验签基座、凭证加密、交付物存储抽象；
- **database**：ORM 基类与命名约定、`session_scope` 事务边界、`Repository`（账号隔离）、`UnitOfWork`；
- **events**：事件信封、进程内总线、事务性 outbox、消费幂等。

为什么这三个域值得抽库？因为它们是**每一刀拆分都重复出现的问题**：错误契约、事务边界、事件一致性。不抽库，八个服务会在第八个服务时出现八种写法。

## 第三步：流量原则——Agent 平台和普通 CRUD 最大的分歧点

普通 SaaS 的流量都是短请求：进来、查库、返回，几百毫秒。Agent 平台不一样：

- 一条「帮我整理周报」消息可能触发 3 分钟的 run；
- 任务的「实时过程」（正在规划、正在调工具、正文流式产出）必须边跑边推给前端。

所以流量原则拆成三条：

1. **普通 CRUD / 短对话**：浏览器 → Nginx → API 网关 → 业务服务，走网关代理没问题；
2. **长任务事件流**：网关**不发任务**，只签发一个短时、单 run 的 stream token，浏览器**直连** orchestrator 的 SSE 端点——避免网关/Nginx 反代层的超时与缓冲把长连接搞死；
3. **服务间调用**：内部 HTTP + 短时服务 JWT，**禁止跨服务直连数据库**。

第三条里有一个容易被追问的细节：账号标识从哪来？答案是**只来自签名 JWT 的 claim**。任何服务都不接受裸的「我是谁」请求头（显式关闭鉴权的部署语义除外）——否则等于给每个服务开了一个伪造身份的后门。

## 第四步：数据边界——账号即隔离边界

多租户隔离在这个体系里是一条硬规则：

- 账号私有表一律混入 `AccountMixin`（带 `account_id` 列）；
- 业务查询一律走 `AccountRepository`，账号过滤由基类自动拼上；
- **跨账号访问一律 404，而不是 403**——不能让攻击者通过状态码区分「存在但无权」和「不存在」；
- 事件信封自带 `account_id`，跨服务消费者按事件里的账号写自己的库，不依赖请求上下文。

这套约束的下限由基类保证，而不是靠每处代码自觉——后面讲仓储那篇会展开。

## 第五步：技术选型的「反直觉」清单

选型最有价值的信息往往不是「用了什么」，而是「为什么不引入某些时髦组件」。真实选型里有几个典型的「不引入」：

| 诱惑 | 决策 | 理由 |
| --- | --- | --- |
| Temporal / Inngest 做长任务 | Postgres job 表 + worker（`FOR UPDATE SKIP LOCKED`） | 队列规模小、事务性和业务库天然一致、少一个运维面 |
| Kafka 做事件 | 事务性 outbox + 进程内总线（阶段 B 换 Redis Streams） | 至少一次语义 + 幂等消费就够，事件量级远没到需要独立 MQ |
| pgvector | JSON 列存向量 + 应用层算相似度 | 文档量级小，检索走词法 + 向量混合，避免为一点数据引入扩展依赖 |
| 托管 IdP（Auth0 等） | 自建 account-service + JWKS | 数据合规、成本、且 OIDC 协议标准后可随时换 |
| WebSocket | SSE + `Last-Event-ID` 续传 | 单向推送够用，HTTP 原生重连语义、代理友好 |

每一条的完整实现都在这个系列的后篇文章里：任务队列（第 2 篇）、事件溯源（第 4 篇）、outbox（第 5 篇）、认证（第 8 篇）。

## 部署形态：同一套代码两种形态

架构要回答的最后一个问题是「卖给谁」。同一套代码支持两种形态：

- **SaaS 形态**：Vercel 托管静态层 + `/api` rewrite，八个 Python 服务跑在云主机 Docker Compose 上，PG/Redis/沙箱在另一台基础设施机（同 VPC）；
- **内网/离线形态**（暂缓）：Linux 裸机 + systemd 原生进程 + Nginx，SQLite + 本地目录，模型可指向内网 OpenAI 兼容端点，无模型时降级为确定性桩仍可启动。

「无模型时系统仍能启动」是个值得单独说的设计决策：所有 LLM 调用走一个 `LLMPort` 接口，`LLM_ENABLED=false` 时注入确定性桩——测试零网络零 token，内网验收可以在禁外网的环境里跑通全流程。

## 几个常见的设计疑问

**「为什么拆微服务而不是单体？」**
先诚实面对拆分成本：八个服务意味着八套迁移、八份监控、网络调用开销。这套架构里拆的理由是三件事确实节奏不同——orchestrator 改图频繁、connector 接第三方风险隔离、llm-gateway 是全局出口必须独立伸缩；同时账号隔离要求「跨服务禁止直连库」，数据库边界反推服务边界。还有一层保底：这个拆法保留了随时合并回单体的能力，共享库层让服务之间的代码复用不需要网络调用。

**「Agent 平台最大的架构风险是什么？」**
不是模型，是**副作用**。模型生成的写操作（建 issue、发评论、写文件）一旦错了是真世界后果。所以整个执行链路上有三道闸：计划审批（run 进 running 前人工放行）、工具风险分级（DANGER 操作绝不直接执行）、确认闸（`awaiting_confirmation` 中断等人工）——第 3 篇和第 13 篇展开。

**「怎么计费？」**
usage ledger：每次模型调用落 token 用量事件，按月聚合查配额，超限 429。BYOK（用户自带 key）走账号级加密存储、网关按账号注入，失败回退平台 key。
